# P0：后期周期性卡顿尖峰分摊

分支 `feature/p0-spread-spikes`（基于 main edc767a）。目标（`docs/architecture/scale-target.md` 第 4 节 P0）：400 单位后期场景模拟每步 p95 ≤ 16 ms，没有 > 40 ms 的尖峰。

## 尖峰从哪里来（改前剖析）

`scripts/perf/late-game.cjs`（coast_l 四国约 400 单位，AI 开，固定指令）逐步计时，挑出 > 25 ms 的步看里面是什么：

| 尖峰 | 周期 | 改前代价（本机） | 原因 |
|---|---|---|---|
| 批量重新寻路 | 每 1.8 s（第 37、73、109… 步） | 35–60 ms，约 220 次 A\* | 一起下令的单位 `repath` 计时器同步，同一步全部重算 |
| 自动索敌扫描 | 每 0.35 s（每第 7 步） | +10–16 ms | 所有单位 `scanAt` 同一时刻起算，同一步一起扫描 |
| 迷雾 | 每 0.5 s（每第 10 步） | 6–20 ms | 四方迷雾一次全算 |
| 电脑 AI | 每 7 s | 15–25 ms | 所有电脑座位在同一步决策 |
| 寻路网格重建 | 建筑出现/倒塌后 | 20–80 ms | 整图逐格 `blocked()`；第二次重建时还要现算地形掩码（约 70 ms） |
| 第 1 步 | 一次 | 100+ ms | 脚本只预热了陆地网格（游戏本身加载时还会预热船的网格），加上冷启动 JIT |

## 做法

全部只依赖模拟状态（`s.time`、单位 id、units 数组顺序），不读真实时间、帧率。

1. **电脑 AI 按座位错开**（dynasties.js `aiTurns`，engine.js 调用点）：每个电脑座位有自己的 7 s 时钟 `s.aiClock[team]`，初始相位在 7 s 内均匀分布（座位 1 保持原相位）。每个座位的决策频率、`nextThink` 门槛、决策内容不变，只是不再挤在同一步。`s.aiClock` 存在状态里，存档/联机服务器重建后继续。
2. **寻路按步预算分摊**（engine.js `pathBudget`）：`walk()` 的寻路每步共用一个预算，每次按 `1 + 路点数/20` 计费（长路径 A\* 展开多）。新路径在已花费 < 36 时可以开始，已有路径的周期重算只在 < 18 时进行（超出的单位沿旧路径多走一步，下步再算）；没轮到的新路径单位原地等一两步。被推迟的单位从那一步起各自计 1.8 s，所以一起下令的大队不会每 1.8 s 再次同步。
3. **A\* 结果共享延长**：同一网格（网格建好后不再修改，变化时整体换新数组）上相同起点格/终点格的查询，结果保留最多 2 s 游戏时间（原来只在同一步内），被预算拆到几步的同一队仍然共用路径。结果与重新计算逐格相同。
4. **自动索敌扫描按 id 错开**（engine.js `slotDelay`）：下次扫描定在该单位 id 在 0.35 s 周期里的固定步上（一个周期后就对齐，扫描频率不变）；另外每步最多 96 次扫描（读档或大批下令后所有单位的扫描时钟都被清零）。
5. **迷雾按队伍错开**（worlds.js `fogTurn` / `updateFog(only)`）：每支队伍仍然每 0.5 s 更新一次，但各在 0.5 s 周期中自己的那一步；`updateFog()` 不带参数时仍是全量更新（事件触发的调用不变）。渲染只看 `fog.revision`，它只在 0 号队伍的视野更新时变化，所以迷雾画布重画频率不变。
6. **寻路网格增量重建**（siege.js `gridDelta`）：建筑变化后的重建从上一张同类网格出发，只对变化建筑（新增、倒塌、换队、换种类）周围 264 px 内的格子重新问 `blocked()`（服务器 `buildNav` 用的是同一个范围，`check-netcode` 逐格验证过）；一个队伍第一次需要城门网格时，从现有的陆地网格（或其他队伍的城门网格）出发，只重算城门和变化建筑周围。世界、联盟关系、网格尺寸变化，或一次变化超过 12 座建筑，都退回整图重建。只在本地模拟里启用（服务器有自己的导航缓存）。
7. **地形掩码预热**（siege.js `prewarmTerrain`）：单位数 ≥ 150 的本地模拟（例如读入后期存档）每步算 4 行地形掩码，第一次网格重建不再一次付出约 70 ms。纯缓存，内容与原来懒计算的完全相同。
8. **测量脚本**：`late-game.cjs` 按游戏加载时的方式预热陆地和船的网格，并输出 `over40` / `over25`；`late-cost.cjs` 汇总 `max`、`over40`；`release-check` 后期一节新增 “>40 ms 尖峰” 检查（中位数 0 为 PASS，1–3 WARN，>3 FAIL）和每步最大值。`late-determinism.cjs --self N` 用于“新版自身多次运行一致”的检查。

没有改数值平衡、兵种、玩法和素材。

## 前后数据

本机是 2 核共享虚拟机（同时有其他任务在跑，机器速度校准比基线日慢 1.16–1.27 倍），所以“改前 / 改后”都用同一个 `scripts/perf/late-game.cjs`（`KINGDOM_ROOT` 指向导出的 main edc767a 即为改前），交替运行（旧、新、旧、新…），只取负载低（1 分钟负载 ≤ 1.2）时的结果。

### Node 后期场景（coast_l 四国 397 单位，600 步 = 30 s，固定指令）

| 指标 | 改前 main edc767a | 改后 本分支 |
|---|---|---|
| 每步均值 | 8.67 ms（8.15 / 8.78 / 8.67） | 8.33 ms（8.33 / 8.32 / 8.74） |
| 每步 p50 | 6.2 ms | 7.3 ms（周期性工作摊进了普通步，预期内） |
| 每步 p95 | **19.3 ms**（19.1 / 20.7 / 19.3） | **15.6 ms**（15.5 / 15.6 / 15.7） |
| 每步最大值 | 101–118 ms | 36–48 ms（都在前 20 步的 JIT 预热里） |
| > 40 ms 步数 | 4–7 次 | 0–1 次（第 20 步之后 **0** 次） |
| 第 20 步之后最大值 | 78–85 ms | 27–33 ms |
| > 25 ms 步数 | 11–18 次 | 3–5 次 |

按机器速度换算到基线机器（release-check 的做法）：改后 p95 13.4 ms、第 20 步后最大 23.5 ms，满足 P0 验收（p95 ≤ 16 ms，没有 > 40 ms 的尖峰）。负载较高的时段（1 分钟负载约 1.3）再测一轮：改前 p95 18.9–22.1、> 40 ms 6–8 次；改后 p95 16.2–17.9、> 40 ms 0–2 次。

工作量没有增加：同一场景 600 步里 A\* 3408 → 3043 次、`blocked()` 81 万 → 67 万次、索敌扫描每次只看附近的格子（与全表扫描比较 26 546 次，选出的目标 0 处不同）。

### release-check（完整模式，`docs/release-reports/2026-11-17-708d31d.md`）

**0 FAIL**（106 PASS、1 WARN：headless 浏览器帧间隔 p50 比基线高 23%，本机负载噪声，与本改动无关的渲染路径）。后期一节：每步均值 8.7 ms、p50 7.46、p95 16.5、第 20 步后 > 40 ms **0** 次、最大 30.2 ms（未校正的本机原始值；校正系数 1.27）；浏览器 sim.tick p95 14.2 ms。

后期 Node 模拟的基线按改后重新取（`node scripts/perf/late-baseline.cjs --write`，只改 `baseline.json` 的 `full.results.late.sim`，其余所有基线不动）：均值 6.38 → 7.16、p50 4.61 → 6.29（分摊的预期结果）、p95 14.19 → 13.38、max 106.8 → 36.0，并新增 `over40Steady: 0`、`maxSteady: 23.54`。release-check 新增的“>40 ms 尖峰（第 20 步后）”检查以 0 为准。

## 确定性

`node scripts/perf/late-determinism.cjs --self 3`：5 个场景（coast_l 9090 / 31337、cliff_s 4242、lake_s 777、straits 2024）各 1200 步，同一份新代码分 3 个进程运行，每 100 步的状态指纹（全部单位 id/兵种/队伍/坐标/血量、建筑、资源点、各方资源）**全部一致**。

与旧 main 的逐位结果不再相同（预期内：AI 决策时刻、寻路和索敌时刻都变了）。网格增量重建另用一个检查验证：4 张地图 AI 对战 10 分钟加上后期场景（含手动加城门触发“从其他网格派生城门网格”），共 317 次增量重建，每次与同一探针的整图重建逐格比较，**0 处不同**。
