## 1. 做了什么

### 中继（服务器端，不运行模拟）

| 文件 | 内容 |
|---|---|
| `server/lockstep/relay-core.cjs` | 与传输无关的中继规则：轮次时钟、封轮（seal）、等待慢玩家（hold）、指令分配轮次、自适应延迟 D（2–5）、指令外壳校验、校验值比对、录像格式 |
| `server/lockstep/http.cjs` | **HTTP 中继（v1 主用）**：`POST /api/lockstep/<房间>`，D1 上 4 张小表；每个请求一次 D1 batch（一个事务、一次往返）；无新轮时最多挂起一个轮次周期（对齐到下一轮边界）。另含 **B2：WebSocket + D1**（`attachSocket`，见第 4 节） |
| `server/lockstep/durable.cjs` | **B1：Durable Object 房间**（内存中继 + 推送 + 同一对象上的 HTTP 轮询回退 + 从 D1 读取房间设置）。**待托管确认后启用** |
| `drizzle/0002_lockstep.sql` | 同样的表结构；代码在首次使用时也会 `CREATE TABLE IF NOT EXISTS`，不依赖托管是否跑迁移 |
| `server/service.cjs` | 大厅 `config.lockstep=true` 的房间开局时只生成开局参数（种子、地图、国家、队伍、座位表、电脑座位、名字），写入锁步表，不建服务器模拟；`/api/lockstep/...` 路由。不勾选的房间完全走旧路径 |

规则要点：
- 每秒 20 步，每 2 步一轮（100 ms）。指令到达中继时分配到“当前仍开放的轮次”；一轮的时间窗过去后被封存，之后内容不再变化，按（轮、座位、序号）顺序发给所有人。
- 指令插入和封轮各是一条 SQL 语句（原子），所以指令绝不会进入别人已经收到的轮次；重发的指令按（座位、序号）去重，丢包重试安全。
- **hold**：某个活跃玩家落后超过 10 轮（1 秒），中继停止封新轮，大家显示“等待 某玩家”。5 秒没有任何请求的座位不再拖住全局（3c 再加 60 秒电脑接管）。
- **延迟 D**：中继按各座位 p90 往返 + 50 ms 推荐 D（2–5 轮，每次只变 1 轮）。D 只决定客户端的回放节奏（“点击后约 D×100 ms 生效”），**指令落在哪一轮只由中继决定**，所以 D 变化不可能导致不同步。这比设计稿第 4 节“全员同一轮切换 D”更简单，效果相同。
- 每 20 步上报 P1 校验值，中继每一步存一行（参照值 + 一致座位位掩码 + 不一致记录），发现不一致时在房间上标记 desync 并下发。
- 录像下载：`POST /api/lockstep/<房间> {replay:1}` 返回开局参数 + 全部指令（`kingdom-lockstep` v1），可无头重放（`KingdomCore.lockstep.replay(rec)` / `replayLockstep`）。

### 客户端

| 文件 | 内容 |
|---|---|
| `src/net/lockstep.js` | 客户端核心（浏览器和 Node 共用）：按开局参数建 Sim（与服务端 start() 相同的构造顺序），按轮执行中继给的指令（`network-commands.js` 的 `execute`），每 20 步算校验值；时钟同步、回放视界、追帧、等待判定、自适应抖动余量 |

**8 客户端 × 10 分钟（加速）**：`node scripts/lockstep/harness.cjs --clients 8 --seconds 600 --period 40`

## 3. 3b 数据（浏览器）

`node scripts/lockstep/browser-duel.cjs --seconds 65 [--delay 100]`，对 `node preview.cjs`。两个 Playwright 上下文，经真实界面：A 勾选“新联机（测试）”建 2 人房 → B 输入房间码加入 → 都准备 → A 开始；之后每人每 2.5 秒按 Q/E 选兵、右键地图，每 3 轮点主城训练村民。

| 场景（1280×720） | 一致 | 点击→执行 | 下令→执行 | 测得 RTT | 其他 |
|---|---|---|---|---|---|
| 无人工延迟 | 76 个校验值相同，无 desync | p50 436 / p90 617 ms | p50 401 / p90 515 ms | 95–115 ms | 1257 次 /api/lockstep 全 200；净荷上行约 280 B/s、下行约 470 B/s；生成视图均值 3.9 ms、最大 41 ms |
| +100 ms 往返 | 74 个相同，无 desync | p50 638 / p90 815 ms | p50 587 / p90 761 ms | 349–406 ms | D 升到 5 |
| 无延迟，480×270 小窗口 | 70 个相同 | — | p50 270 / p90 325 ms | 44–52 ms | 渲染负担小时延迟明显下降 |

测量方法：“点击→执行”= Node 在 `mouse.click` 之前取时间戳，到该页锁步模拟执行这次点击产生的 `orders` 指令的时间（同一台机器时钟）；“下令→执行”= 页面内 `issue()` 到执行。人工延迟用 Playwright `context.route` 对每个 /api/lockstep 请求先等 50 ms 再发、收到后再等 50 ms 交付。

**结论：浏览器里本机加 100 ms 延迟时操作延迟 ≤ 200 ms 未达到。** 原因在本机环境：两个 headless Chromium 标签页在 2 个 vCPU 上软件渲染整局游戏，主线程很忙，网络回调要排队。对照：同一页面进入对局后，单纯 `fetch('/api/health')` 往返就要 90–370 ms（主菜单时 3–30 ms）；所以测得的 RTT 本身就有 100 ms 左右，自适应逻辑据此把 D 和抖动余量调大（这是设计的行为：宁可稍慢也不卡顿）。协议本身在没有渲染负担的 Node 客户端上，+100 ms 往返时 p50 200 ms。玩家点击时的语音、标记、转身仍是即时的（本地预测）。

需要的后续：(1) 真机（iPhone + 电脑）测同样两个数字（3d 的验收）；(2) 如果真机主线程也拖慢，把锁步模拟和网络放进 Web Worker（主线程只渲染），这是 3c/3d 的候选优化。

**旧联机冒烟**（`node scripts/replay/live-online.cjs 65`，含 3 个电脑座位）：POST 201 ×1、200 ×246，**无 503、无页面错误**，游戏时间 1.5 → 75.2 秒，4 国；preview 日志无 error。

## 4. 两种传输的现状

| 传输 | 状态 | 说明 |
|---|---|---|
| HTTP 轮询（D1） | 自动回退路径（v2 前为默认）；本地全部验收通过 | 只用现有 fetch(request, env) + D1，必定能在现托管上运行 |
| B2：WebSocket + D1 | **新联机默认（大厅 v2 起）**；本地通过（含被平台断开后重连补帧、回退 HTTP）；Sites 已实测可用（见第 5 节实测结论）；`LOCKSTEP_TRANSPORT=http` 可关闭 | 每个连接在接受它的 isolate 里，每到轮次边界做一次和 HTTP 相同的 D1 交换并推送新轮；跨连接状态全在 D1，同一房间的连接可以在不同 isolate、甚至一部分是 HTTP 客户端，结果都一致。**不依赖 isolate 共享内存**。省掉了 HTTP 头开销，D1 负载与 HTTP 轮询相同（每连接每轮一次 batch） |
| B1：Durable Object | 代码完成、本地用内存对象通过；**未接线** | 需要：wrangler 里 `durable_objects` 绑定 `LOCKSTEP` + migration；Worker 入口具名导出 `LockstepRoomDurable`（现在的 `scripts/build.cjs` 只导出 default，需要小改）。有绑定时，该房间的 socket 和 HTTP 轮询都进同一个对象，回退也一致 |

自动回退规则：ws 3 秒内打不开（两次）或 10 秒内断 3 次且 3 秒没收到轮次 → 本局改用 HTTP。平台到时断开 → 立即重连，hello 带最后轮次，中继补发；已发未确认的指令重发（按座位+序号去重）。

## 8. 3c：断线恢复、电脑接管、不同步处理、联机存档（2026-11-20，分支 `feature/p3c-resilience`，基于 main b1077e0）

数据标注：除特别说明外都是**本机测量**（2 vCPU 共享虚拟机，Node 22.23，headless Chromium），线上 D1 用模型代替（`scripts/lockstep/d1-sim.cjs`：每次 D1 调用加延迟 + 每次 Worker 调用的 D1 次数上限）。**不是 Sites 线上或真机数据。**

### 8.1 线上故障：第 16 分 43 秒起“等待网络… 213s”，再也连不上

**根因**：WebSocket + D1（B2）里，一条 WebSocket 连接在 Worker 里是**一次调用（invocation）**，从连上到断开都算同一次。中继在这条连接上每到轮次边界（100 ms）做一次 D1 交换，一分钟 600 次。平台对单次调用能发出的子请求 / D1 调用次数有上限（Cloudflare 报错 “Too many API requests by single worker invocation”）；按每秒 10 次算，上限约 10 000 次时正好在 **约 16.7 分钟**用完——与用户截图的 16:43 吻合（用户之前的 Q2 实测“连接 15 分钟不断”是只发 ping、不访问 D1 的探针，所以没碰到）。用完之后每次 D1 调用都抛错，而旧代码：
1. `attachSocket` 的 `tickNow` 把错误吞掉，**连接保持打开但不再推送任何轮次**；
2. 客户端没有“连着但没数据”的看门狗，回退 HTTP 的规则只看“反复断开”，所以既不重连也不回退；
3. 结果就是永远“等待网络…”，秒数一直涨。

> 平台的确切上限值无法在本机验证（需要 Sites 文档或线上日志）；但不管上限是多少、还是别的原因让 D1 持续失败，第 2、3 条“静默挂死”都是确定的缺陷，已全部修掉。

其他候选原因逐一排除：
| 候选 | 结论 |
|---|---|
| 房间码租约 / 30 分钟回收 | 锁步中继只认 `lockstep_rooms`（6 小时有效期），不读大厅短码表；短码过期只影响“用 3 位码加入”，不影响进行中的对局（代码审查 + 26 分钟长局实测） |
| 指令/轮次表增长、缺索引、单次返回超限 | 按轮次取新数据走索引 `lockstep_cmds_turn (room, turn)`（EXPLAIN 见下）；90 分钟 8 人的合成数据下实时交换 p50 0.14 ms，与表大小无关；单次最多 2000 行，追帧分批 |
| WebSocket 被断开后重连失败 / catchup 太大 | 旧代码平台断开时会立即重连补帧（3b 已测）；本次故障里连接**没有断开**，所以不是这条路径 |
| iPad 切后台 | 后台时页面冻结、连接可能还开着；旧中继每个轮次用自己的时钟刷新 `seen`，冻结的客户端会一直“在线”。本次一并修复（presence 改为客户端最后一条消息的时间） |
| 托管方停止空轮心跳 | 锁步里电脑座位由每台设备本地计算，没有托管方；中继按墙钟封轮，不依赖任何客户端发心跳 |

**复现**（`docs/p3c/repro-before.json`）：`node scripts/lockstep/harness.cjs --clients 3 --seconds 1100 --period 25 --transport ws --d1-latency 12 --invocation-limit 10000 --stall 20`（4 倍加速，D1 延迟 47 ms 按比例缩到 12 ms，每次调用 10 000 次 D1 上限）：3 个客户端都卡在第 ~7745 轮（加速下 hold 让墙钟轮次多于游戏轮次，所以比 16.7 分钟早），**0 次重连**，平台拒绝了 2298 次 D1 调用。

**修复**：
- 中继：每条 socket 计数自己的 D1 调用，到 `SOCKET_BUDGET`（默认 2400，约 4 分钟）就发 `{type:'reconnect'}` 并关闭，客户端立即用新连接（新的调用）续上，hello 带最后收到的轮次补发；连续 3 次交换失败直接关闭（1011），任何 D1 / 平台故障都会变成重连而不是静默；无新轮时也每 1 秒推一次 `turns` 心跳；`seen` 用客户端最后一条消息的时间。顺带修了 `tickNow` 在交换跨过轮次边界时会多挂一条定时器链的问题。
- 客户端：看门狗（连接打开但 4 秒没有 `turns` → 关掉重连）；计划内重连不算掉线；意外断开指数退避 0 / 250 / 500 ms / 1 / 2 / 4 / 8 s，之后每 10 秒；页面回到前台、网络恢复（`visibilitychange` / `online` / `pageshow`）立即检查；曾经连上过的 socket 遇到断网会一直按退避重试（不回退 HTTP，HTTP 断网时同样失败）；HTTP 传输失败也改为指数退避（以前每 25 ms 重试一次）。

**修复后同一场景**（`docs/p3c/repro-after.json`）：11 000 轮全部跑完，每客户端 6 次计划内重连，平台拒绝 0 次，3 × 1100 个校验值一致，录像无头重放 52425a3a 一致。
