# 《边境王国》目标规模与架构路线图

本文是架构层面的权威文档。所有 AI（Claude、Codex 等）在做影响性能、联机、数据结构和渲染的改动前，都必须先读本文，并遵守第 2 节的预算。

## 1. 目标规模（项目负责人 2026-11-17 确定）

| 项目 | 目标 |
|---|---|
| 玩家数 | 最多 8 人（真人和电脑任意组合） |
| 单位规模 | 全图最多 1000 个单位（含村民、军队、船） |
| 对局时长 | 跟人数和地图挂钩：2 人小图约 10 分钟，8 人最大图约 90 分钟 |
| 平台 | 电脑浏览器（包括 32 寸大屏）、iPhone、iPad；以后打包上 Steam 和 App Store |
| 联机 | 朋友之间联机，操作手感接近单机，掉线可以重连 |

地图尺寸按人数分档（像素尺寸只是建议，以资源密度和行军时间为准）：

| 人数 | 地图档位 | 建议尺寸 | 目标时长 |
|---|---|---|---|
| 2 | 小 | 约 4800×3456（现有） | 10–20 分钟 |
| 3–4 | 中 | 约 7200×5000（现有最大） | 25–40 分钟 |
| 5–6 | 大 | 约 9600×6600 | 45–60 分钟 |
| 7–8 | 特大 | 约 12000×8400 | 60–90 分钟 |

时长靠资源总量、行军距离和时代推进节奏来控制，不靠人为拖延。

## 2. 性能预算（每次发布前用 release-check 检查）

| 指标 | 预算 |
|---|---|
| 模拟频率 | 固定每秒 20 步（每步 50 ms 游戏时间） |
| 模拟每步耗时（1000 单位、8 方，中端电脑） | 平均 ≤ 8 ms，p95 ≤ 16 ms |
| 渲染 | 电脑 60 帧（每帧 ≤ 16 ms），手机和 iPad ≥ 30 帧；同屏 300 个单位时仍满足 |
| 内存 | 电脑 ≤ 400 MB，手机 ≤ 300 MB |
| 首次加载 | ≤ 10 秒（素材按需加载） |
| 联机操作延迟 | 指令到单位动起来 ≤ 200 ms（同城网络） |
| 联机带宽 | 每个玩家 ≤ 2 KB/s（只传指令） |
| 服务器 | 每局只做转发和存档，CPU 不随单位数增长 |

现状（2026-11-17，`feature/late-game-perf`）：400 单位时模拟每步平均 8.3 ms、p95 18.5 ms；内存约 800 MB；联机是 HTTP 轮询，服务器每次请求都从存档重建整局。**现有架构达不到 1000 单位和 8 人的目标**，需要按第 4 节分阶段改造。

P0 结果（2026-11-17，`feature/p0-spread-spikes`，见 `docs/p0-spread-spikes.md`）：电脑 AI 按座位错开、寻路每步预算、索敌和迷雾按 id/队伍错开、网格增量重建。400 单位后期场景（本机，交替测量）每步均值 8.7 → 8.3 ms，p95 19.3 → 15.6 ms，最大 101–118 → 36–48 ms（只在开局 1 s 的 JIT 预热里），第 20 步之后 > 40 ms 的步 4–7 次 → 0 次；按机器速度换算到基线机器 p95 13.4 ms。P0 验收达成；电脑对电脑强度与改前接近。

P1 结果（2026-11-17，`feature/p1-foundations`，见 `docs/p1-foundations.md`）：**1000 单位基准（5 国 × 200 单位，座位上限 5，军队分 8 组在 4 条战线对冲，coast_l，AI 开）每步均值 22.0–22.3 ms、p50 20–21 ms、p95 32.7–33.2 ms、最大 67–75 ms，第 20 步后 >40 ms 4–11 次**（本机 Node，600 步 × 3 次中位数，两次完整 release-check）——均值超预算约 2.8 倍、p95 约 2 倍，留给 P5；release-check 只记录（INFO/WARN）。录像回放（4 张地图各 60 s，含玩家指令）3 次一致且与录制时校验值相同；校验值每 20 步一个（FNV-1a，按 id 排序、1/100 量化）。跨引擎：Chromium 与 Node 一致；WebKit/Safari/iPhone 尚未验证（本机没有 WebKit），方法见 p1-foundations.md 第 6 节。
P2 素材流水线结果（2026-11-17，`feature/p2-asset-pipeline`，测法见 `docs/p2-asset-pipeline.md`）：首次加载到可玩（20 Mbit/s、40 ms）43.5 s → 9.8 s；部署包 270 → 76 MB；图集解码像素总量 775 → 447 MB（首屏 207 MB）；后期 412 单位场景渲染进程内存（无头 Chromium）约 1400 → 960 MB，**仍未达到 400 / 300 MB**，剩余主要是逐帧缓存画布（约 310 MB）和解码过程的分配器占用，需 P6 渲染改造继续压。
内存预算与真机一致性（2026-11-17，`feature/memory-and-device-check`，见 `docs/memory-budget.md`、`docs/device-consistency-check.md`）：图集改为 `createImageBitmap` 解码进画布（不再在 Chromium 的可丢弃共享内存里常驻约 2 倍像素的解码缓存），所有运行期派生画布缓存（队伍色、攻击动作集、点选遮罩/幽灵、步态帧、建筑变体等 17 个）纳入一个全局 LRU 字节预算（电脑 160 MB、触屏 96 MB、低内存设备 64 MB）。后期 412 单位场景渲染进程内存（无头 Chromium，同一测法）电脑 **955 → 666 MB**、手机配置 **961 → 629 MB**，渲染耗时未变差（late-render render p50 26 → 22 ms）；**仍未达到 400 / 300 MB**：剩余约 284 MB 渲染进程地板、约 190 MB 启动时切好的常驻帧图和地形烘焙（留给 P6）、约 136 MB 预算内缓存。新增 `/consistency.html`：在任意浏览器里回放 3 段标准录像（战斗/建造/经济，40–60 s），每 1 秒对照 Node 生成的校验值，供 iPhone/iPad/Safari 真机自测；Chromium 全部一致，Safari 待用户真机结果。

## 3. 目标架构

```
┌──────────── 浏览器 / Steam 外壳 / iOS 外壳 ────────────┐
│  主线程：输入 → 指令队列 ─────────┐                     │
│          渲染（WebGL 批量绘制，    │                     │
│          在两次模拟之间插值）◄─────┼── 状态快照（只读）   │
│  Web Worker：确定性模拟（固定 20 步/秒）                 │
│     · 数据：按列存的紧凑数组（ECS）                      │
│     · 空间网格：索敌、碰撞、视野                         │
│     · 寻路：分层 A* + 同目标共用流场                     │
│     · 电脑 AI：只能下指令，计算按帧分摊                  │
└────────────────────────────────┬────────────────────────┘
                                 │ 只传“第 N 步、谁、下了什么指令”
                   WebSocket 中继（Cloudflare Durable Object）
                   · 收集各方指令并按步广播
                   · 定期接收状态校验值，发现不同步就报警
                   · 保存指令录像，用于重连和回放
```

关键原则：
1. **确定性**：模拟只用种子随机数和整数或定点运算，输出只取决于“初始状态 + 指令序列”。这是锁步联机、录像回放和不同步检测的共同基础，任何改动都不能破坏它。
2. **模拟和渲染分离**：模拟在 Worker 里按固定步长运行，渲染只读快照并插值。画面卡不会拖慢游戏，游戏忙也不会让画面掉帧。
3. **玩家和电脑都只能下指令**：AI 和真人走同一个指令接口。这样公平，AI 也可以单独限制计算预算。
4. **服务器不跑游戏**：只做中继、存档和校验，8 人局的服务器成本和 2 人局差不多。
5. **按需加载素材**：只加载本局用到的国家和兵种，图片按实际显示尺寸生成，图集按国家打包。

## 4. 分阶段路线图

> 详细执行计划、成本估算和迁移策略见 `redesign-plan.md`（v1, 2026-11-17），阶段顺序以该文件为准。

每个阶段都要先加上对应的 release-check 场景，再动手改；只有达标后才进入下一阶段。

| 阶段 | 内容 | 验收标准 | 依赖 |
|---|---|---|---|
| P0 | 合并 late-game-perf；电脑 AI 决策和批量寻路按帧分摊，消除周期性卡顿 | 400 单位时模拟 p95 ≤ 16 ms，没有 >40 ms 的尖峰 | 无 |
| P1 | **录像回放 + 状态校验值**：记录指令序列，可逐帧重放；每 N 步算一次状态校验值 | 同一份录像重放 3 次，结果完全一致；release-check 新增“回放一致”检查 | P0 |
| P2 | **素材流水线**：构建时把图片缩到显示尺寸、按国家打包图集、按局按需加载、清理废弃素材 | 内存 ≤ 400 MB，首次加载 ≤ 10 秒，画质由艺术总监目测通过 | 无（可以和 P1 并行） |
| P3 | **联机改为锁步**：WebSocket + Durable Object 中继，只传指令；断线后用录像追帧重连；校验值不一致就报警 | 8 人 1000 单位：带宽 ≤ 2 KB/s/人，操作延迟 ≤ 200 ms，服务器 CPU 不随单位数增长；双设备真机测试通过才能给玩家用 | P1 |
| P4 | **模拟移进 Web Worker + 固定步长 + 渲染插值** | 主线程每帧 JS ≤ 8 ms；模拟卡顿不再造成掉帧 | P1 |
| P5 | **数据改为按列存储（ECS）+ 流场寻路**（同一目标的大批单位共用一张方向图） | 1000 单位时模拟平均 ≤ 8 ms、p95 ≤ 16 ms | P4 |
| P6 | **WebGL 批量渲染**（如 PixiJS），沿用现有素材 | 同屏 300 单位时电脑 60 帧、iPad ≥ 30 帧 | P2 |
| P7 | **8 人地图档位 + 时长平衡**：大和特大地图、资源分档、时代节奏 | 用电脑对电脑的模拟统计对局时长，各档落在第 1 节的目标区间 | P3、P5 |
| P8 | **平台外壳**：Steam（Tauri 或 Electron）、iOS（Capacitor），加真机性能遥测 | 三个平台用同一份核心代码 | P6 |

建议执行顺序：P0 → P1 和 P2 并行 → P3 → P4 → P5 → P6 → P7 → P8。

## 5. 给 AI 的工作规则（补充 AGENTS.md）

- 新功能先说明它属于哪个模块（模拟、渲染、联机、AI、素材、界面），以及会不会违反第 2 节的预算或第 3 节的原则，然后再写代码。
- 模拟层的任何改动都要通过确定性检查（`scripts/perf/late-determinism.cjs`，P1 之后再加录像回放检查）。
- 不允许再新增“层层包装全局函数”式的补丁；新的绘制效果、声音、AI 行为都要通过明确的注册点接入（P4 时建立插件注册表）。
- 每完成一个阶段，更新本文第 2 节的“现状”。重要的技术取舍写进 `docs/architecture/decisions.md`，每条一段：背景、选择、放弃了什么、为什么。
