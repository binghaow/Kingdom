# 《边境王国》架构重设计计划 v1

作者：Claude（高级游戏架构师角色），2026-11-17。目标规模见 `scale-target.md`：8 人、1000 单位、对局 10–90 分钟；平台包括电脑、iPhone/iPad，后续上 Steam 和 App Store。

本文是执行计划。目标和预算以 `scale-target.md` 为准；两份文档冲突时，以本文的阶段顺序为准。

---

## 1. 现状诊断（基于 main edc767a 的实测与代码统计）

| 方面 | 现状 | 对目标的影响 |
|---|---|---|
| 代码规模 | 浏览器端 109 个 JS 文件，约 1.1 MB；`index.html` 用 97 个 `<script>` 标签按顺序加载，全部挂在全局变量上 | 加载顺序就是隐形依赖，改错一处整页白屏（11-12 的分号事故就是这种） |
| 模拟层 | `engine.js` 定义 Sim，约 20 个模块通过 `require` 链逐层继承扩展（如 network-model → ai-humanlike → frontier-v40 → roster → …），服务器端用 Node 直接运行同一份代码 | **好消息**：模拟已经能脱离浏览器运行，而且是确定性的（late-game-perf 已证明逐位一致）。**坏消息**：继承链很深，每层都可能覆盖 tick，执行顺序和开销都不透明 |
| 渲染层 | Canvas 2D。`A.unit` 被 21 个模块层层包装，`A.building` 12 层，`A.node` 8 层 | 每画一个单位要穿过 21 层函数，到 1000 单位时开销成倍增加；新增效果必须精确插入某一层（例如单位缩放必须放在 precision-picking 之前） |
| 数据 | 每个单位是一个大对象，几十个字段，放在数组里 | CPU 缓存不友好，难以搬进 Worker 或共享内存 |
| 联机 | HTTP 轮询；服务器（Worker + D1）每次请求都从存档恢复整局再推进 | 服务器 CPU 随单位数和人数增长；8 人局不可行；延迟高 |
| 素材 | `public/assets` 246 MB（134 张图集，解码后约 820 MB），开局全部加载；`public/audio` 31 MB | 内存 800 MB，手机和车机吃紧，加载慢 |
| 质量保障 | 54 个 check 脚本，加上 release-check（路径、模拟、渲染、联机、后期场景） | **优势**：护栏已经很全，重构可以放心推进 |

结论：模拟层的确定性和可独立运行，是最值钱的资产，必须保留。真正的瓶颈在三处：联机模型、渲染管线、数据布局。加载方式和素材是放大器，会把这三处的问题放大。

## 2. 目标架构

```
packages（按目录分层，esbuild 打包；依赖只能从上往下）
├─ core/        确定性模拟：纯逻辑，没有 DOM，没有真实时间
│   ├─ ecs/       单位、建筑、资源按列存（TypedArray），id→索引表
│   ├─ systems/   按固定顺序执行的系统：指令→AI→移动→寻路→战斗→经济→视野→胜负
│   ├─ spatial/   均匀网格：索敌、碰撞、视野、建筑占位
│   ├─ path/      分层 A*（区块→格子）+ 流场（同目标的大批单位共用）
│   └─ rng/hash   种子随机数、状态校验值
├─ commands/    指令格式（玩家和 AI 共用），序列化和校验
├─ ai/          电脑玩家：读状态快照，只输出指令，每步有计算预算
├─ net/         锁步客户端：指令延迟缓冲、追帧、不同步检测、重连
├─ render/      WebGL 批量渲染（PixiJS）：渲染通道注册表，在两次模拟之间插值，按距离降细节
├─ ui/ audio/   界面和声音：只订阅事件和快照
├─ assets/      素材清单，按局按需加载，图集管理
└─ shells/      web / steam（Tauri）/ ios（Capacitor）
server/         Durable Object 中继：转发指令、保存录像、比对校验值，不跑模拟
```

运行时线程：
- **Worker 线程**：core 加 ai，固定每秒 20 步。
- **主线程**：输入、渲染（60 帧，插值）、界面、声音。
- 两个线程之间只传两样东西：指令（主线程 → Worker）和快照（Worker → 主线程，可以先用复制，后续改为 SharedArrayBuffer 共享）。

五条铁律：
1. core 不能 import render、ui、net。
2. 只有指令能改变模拟状态。
3. 模拟里不能出现真实时间、`Math.random` 或帧率相关的分支。
4. 渲染和界面效果都通过注册表接入，禁止再包装全局函数。
5. 每项改动都要过性能预算和确定性检查。

## 3. 迁移策略：绞杀者模式，不推倒重来

- **游戏全程可玩**：每个阶段结束时，main 都能直接发布。
- **新旧共存**：新代码用 ES 模块写在 `src/` 下，由 esbuild 打包；旧的全局脚本暂时保留，通过一个桥接层互相调用，再按模块逐个迁移，迁完一个删一个。
- **用录像做安全网**（P1 之后）：每次迁移模拟代码，都要回放一批标准录像，最终状态的校验值必须和迁移前完全一致。录像确实需要更新时，要单独说明理由。
- **用开关切换新旧实现**：例如新渲染器用 `?renderer=webgl` 开启，并排对比稳定后再改为默认。

## 4. 分阶段执行方案与成本

成本有两种口径：
- **人工**：一名资深工程师全职的工作量，单位是周。
- **AI**：按本项目实测，一次程序员 agent 会话约 1–1.5 小时、消耗约 25–32 万 token。

估算误差约 ±30%。联机和渲染两项风险最高，误差也最大。

| 阶段 | 内容 | 验收标准 | 人工 | AI 会话 / token | 风险 | 依赖 |
|---|---|---|---|---|---|---|
| **P0** 消除尖峰（进行中） | AI 决策和批量寻路按步错开，其他定时任务也错开 | 400 单位时 p95 ≤ 16 ms，没有超过 40 ms 的帧 | 0.5 | 1 / 约 0.3M | 低 | — |
| **P1** 地基（已完成，`feature/p1-foundations`，见 `docs/p1-foundations.md`；WebKit/iPhone 跨引擎一致性待真机） | ① esbuild 打包，新代码用 ES 模块，旧全局脚本桥接；② 录像（指令序列）录制和回放；③ 每 N 步一次状态校验值；④ 新增 1000 单位、8 方的基准场景，纳入 release-check | 同一份录像重放 3 次结果完全一致；打包后体积和加载时间不变差；1000 单位基准场景能跑出数据 | 2 | 3 / 约 0.9M | 低 | P0 |
| **P2** 素材流水线 | 构建时按实际显示尺寸缩放图片，按国家和兵种拆分图集，按局按需加载，图片改用 WebP 或 AVIF，删除废弃素材，音乐改为流式播放 | 内存：电脑 ≤ 400 MB、手机 ≤ 300 MB；首次加载 ≤ 10 秒；艺术总监目测画质无明显下降 | 1.5 | 2 / 约 0.6M | 低 | 可与 P1 并行 |
| **P3** 锁步联机 | WebSocket + Durable Object 中继；指令按步打包，延迟 2–4 步；断线后用录像追帧重连；校验值不一致时报警并上报；服务器不再运行模拟 | 8 人、1000 单位：每人 ≤ 2 KB/s，操作延迟 ≤ 200 ms，服务器 CPU 与单位数无关；**两台真机实测通过后，才对玩家开放** | 3–4 | 5 / 约 1.5M | **高** | P1 |
| **P4** 模拟核心重组 | 把约 20 层继承链改成按固定顺序执行的系统管线；统一指令接口（AI 改为只下指令）；模拟搬进 Worker，固定步长，渲染插值 | 录像校验值和迁移前一致（或有说明的可控变化）；主线程每帧 JS ≤ 8 ms；模拟卡住时画面不卡 | 4 | 5 / 约 1.5M | 中高 | P1，最好在 P3 之后 |
| **P5** 千兵规模 | 数据改为按列存储（ECS、TypedArray）；空间网格成为统一服务；分层 A* 加流场；AI 计算预算 | 1000 单位：平均 ≤ 8 ms，p95 ≤ 16 ms | 3–4 | 5 / 约 1.5M | 中 | P4 |
| **P6** 渲染重写 | PixiJS 批量渲染，精灵图集；渲染通道注册表取代 21 层包装；远处单位降细节；地形分块预烘焙 | 同屏 300 单位：电脑 60 帧，iPad ≥ 30 帧；所有现有视觉效果都迁移完成，由艺术总监验收 | 5–6 | 7 / 约 2.1M | **高**（工作量最大） | P2、P4 |
| **P7** 8 人地图与时长 | 大和特大两档地图，资源与行军距离分档，时代节奏调整；用电脑对电脑模拟统计对局时长 | 各档时长落在目标区间；资源公平性检查通过 | 2–3 | 3 / 约0.9M | 中 | P3、P5 |
| **P8** 平台与遥测 | Steam 外壳（Tauri）、iOS 外壳（Capacitor）；真机帧时间、内存和崩溃遥测；存档版本化 | 三个平台共用一份 core；遥测面板可用 | 2–3 | 3 / 约 0.9M | 中 | P6 |
| **合计** | | | **约 23–28 周** | **约 34 次 / 约 10M token** | | |

关键路径：P0 → P1 → P3 → P4 → P5 → P6 → P8，约 20 周。P2 和 P7 可以和其他阶段并行。

**里程碑和每阶段完成后你能感受到的变化：**
- **M1（P0–P2，约 4 周）**：后期不再周期性卡顿；内存减半；加载变快；出了 bug 可以用录像复现。
- **M2（P3，约 +4 周）**：联机延迟大幅下降，8 人房间可以开。这是你最在意的联机体验。
- **M3（P4–P5，约 +8 周）**：1000 单位不卡；电脑 AI 不再拖慢画面。
- **M4（P6–P8，约 +10 周）**：大屏幕和 iPad 满帧；8 人大地图；可以上 Steam 和 App Store。

**运行成本**：锁步联机之后，服务器只转发指令。8 人局每秒只有几十条小消息，服务器费用远低于现在每次请求都要重算整局的方案。具体费用以 Cloudflare 当时的定价为准。

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| 浮点运算在不同 CPU 或浏览器上结果不一致，锁步联机出现不同步 | P1 先在 Chrome、Safari 和 iPhone 上用同一份录像比对校验值；出现差异的数学运算改为整数或定点运算；P3 上线前必须用真机跨平台对局 |
| 重构过程中玩法悄悄改变 | 录像校验值做门槛，再加电脑对电脑胜率和出兵统计的对比 |
| 渲染重写后丢失视觉效果 | 先盘点所有效果（21 层包装各管什么），逐项迁移，`?renderer` 开关并排对比，艺术总监逐项验收 |
| 工作量大、token 消耗高 | 严格按阶段推进，每阶段只开 1 个程序员；每阶段完成后由你试玩，确认再继续；暂停时游戏仍可发布 |
| 联机改造期间老版本联机受影响 | 新旧联机并存，新联机用开关开启，稳定后再切换为默认 |

---

## 6. 现在就该停止的做法

- 不再新增“包装全局函数”的补丁。新效果暂时集中注册到一个文件，等 P6 时统一迁走。
- 不再在 `index.html` 里继续追加 `<script>`。新代码从 P1 开始放进 `src/`，由打包器统一管理。
- 模拟代码不再引用 DOM、`performance.now()` 或 `Math.random`。
- 素材不再直接以原图尺寸进入 `public/assets`，必须经过 P2 的流水线。

## 7. 下一步

P0 完成后，同时启动 P1（地基）和 P2（素材流水线），各由一个程序员负责，两者互不冲突。P1 完成后进入 P3（锁步联机）。
