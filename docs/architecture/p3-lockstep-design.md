# P3 锁步联机设计 v1

状态：设计稿（2026-11-17）。开工前必须满足两个前提：
1. iPhone / iPad / Safari 打开 `/consistency.html`，结果为“全部一致”。不一致时，先把出现差异的计算改成整数或定点运算，再开始 P3。
2. P0–P2 已上线，并经过真机试玩。

目标见 `scale-target.md`：8 人、1000 单位；操作延迟 ≤ 200 ms；每人带宽 ≤ 2 KB/s；服务器 CPU 不随单位数增长。

---

## 1. 现状与要替换的部分

- **现状**：HTTP 短轮询 + D1 乐观锁，服务器权威（见 `docs/netcode-p0.md`）。每次请求，服务器都要从存档恢复整局、推进模拟、再按视野过滤后返回快照，每次 10–55 KB。
- **保留不动**：房间创建和加入（`/api/rooms`）、座位和国家选择、D1 里的房间元数据、现有的大厅界面。
- **要替换**：对局开始后的同步方式。快照轮询改为指令锁步，服务器从“跑游戏”改为“排队转发”。

## 2. 核心思路

每台设备都运行同一份确定性模拟。服务器只做三件事：
1. 收集每一步各方的指令；
2. 把同一步的所有指令按固定顺序广播给每个人；
3. 收集状态校验值，比对是否一致。

只要初始状态和指令序列相同，所有设备算出的结果就一定相同。这一点已由 P1 的录像回放验证。

## 3. 组件

| 组件 | 位置 | 职责 |
|---|---|---|
| 中继 `LockstepRoom` | Cloudflare Durable Object（每个房间一个实例） | 维护 WebSocket 连接，给每一步编号，汇总指令，广播，保存录像，比对校验值 |
| 房间 API | 现有的 `server/service.cjs` | 大厅、座位、开局参数（种子、地图、国家、难度）；开局后把客户端引导到 Durable Object |
| 客户端 `net/lockstep` | `src/net/`（P1 打包管线） | 连接中继，管理指令缓冲，按步驱动模拟，处理追帧、重连和不同步上报 |
| 电脑玩家 | 每台设备本地运行 | AI 由种子决定，所有设备各算一份，结果相同，不需要传输（P1 已验证） |

## 4. 时间模型

- **模拟步长**：每秒 20 步，每步 50 ms 游戏时间，与 `scale-target.md` 一致。
- **轮次**：每 2 步为一轮（100 ms）。中继每 100 ms 发出一个“第 N 轮指令包”。
- **指令延迟**：玩家在第 N 轮下的指令，在第 N + D 轮生效。D 默认为 2（约 200 ms），按网络情况自适应调整：
  - 中继统计各方的往返延迟，取 p90 + 50 ms，换算成轮数；
  - 调整范围 2–5 轮；
  - 每次只调整 1 轮，并广播给所有人，所有人在同一轮切换。
- **即时反馈，掩盖延迟**：下令时立即播放语音、显示点击标记和单位转身动画。这些只是表现层效果，不改模拟状态，所以看起来是即时的。现有的本地预测代码可以复用。

## 5. 消息（WebSocket，JSON；稳定后可改为二进制）

| 方向 | 消息 | 字段 | 说明 |
|---|---|---|---|
| 客户端 → 中继 | `hello` | 房间、座位、令牌、协议版本、最后收到的轮次 | 连接或重连 |
| 中继 → 客户端 | `start` | 种子、地图、座位表、开局参数、起始轮次、D | 所有人就绪后发出 |
| 客户端 → 中继 | `cmd` | 目标轮次、座位、指令数组（P1 的指令格式） | 没有指令就不发 |
| 中继 → 客户端 | `turn` | 轮次、按“座位 → 序号”排好的指令数组 | 每 100 ms 一条；空轮也发，作为心跳 |
| 客户端 → 中继 | `hash` | 步号、校验值 | 每 20 步发一次（P1 校验值） |
| 中继 → 客户端 | `desync` | 步号、各方校验值 | 发现不一致时发出 |
| 客户端 → 中继 | `ping` / 中继 → 客户端 `pong` | 时间戳 | 测量延迟，用于调整 D |
| 中继 → 客户端 | `catchup` | 从第 K 轮到当前轮的全部指令 | 重连或掉队时补发 |
| 中继 → 客户端 | `seat` | 座位状态：在线、掉线、AI 接管 | 有人掉线时发出 |

**带宽估算**：一轮通常只有 0–3 条指令，每条约 40–80 字节。每人上行通常不到 0.5 KB/s，下行 8 人合计约 1–2 KB/s，满足 ≤ 2 KB/s 的预算。

## 6. 关键流程

**开局**：
1. 大厅选好座位后，房间 API 生成种子和开局参数，写入 D1；
2. 客户端连接 Durable Object，发送 `hello`；
3. 全部座位就绪后（超时则由 AI 接管空座位），中继发出 `start`；
4. 所有人在同一轮开始模拟。

**每一轮**：
1. 客户端在轮次 T 收到 `turn`，把其中的指令放入第 T 轮执行；
2. 本地推进 2 步；
3. 如果本地模拟落后（比如手机卡了一下），就加速多跑几步追上；如果第 T 轮的指令包还没收到，就暂停模拟等待，画面继续插值，最多等 1 秒；
4. 等待超过 1 秒时，画面显示“等待某玩家”。

**断线重连**：
1. 中继保留整局的指令录像（存在 Durable Object 的存储里，定期备份到 D1 或 R2）；
2. 客户端重连后发送 `hello(最后轮次)`，中继用 `catchup` 补发缺少的指令；
3. 客户端快速重放追上进度（无头模式，不渲染）；
4. 掉线超过 60 秒，该座位由 AI 接管，回来后可以收回控制权。

**刷新页面或换设备重连**：从第 0 轮开始重放全部指令。一局 90 分钟约 54000 轮，按 P1 的回放速度估计需要数秒到数十秒，界面显示进度条。以后可以加“中继每 5 分钟保存一次状态快照”来缩短时间，属于优化项。

**不同步**：
1. 中继发现同一步的校验值不一致，通知所有人，并保存录像和各方校验值，用于排查；
2. 处理策略：v1 版本以多数方为准，把少数方踢回大厅并提示；v2 版本由中继下发权威快照进行重同步（需要快照序列化）。
3. 所有不同步事件都要上报，作为 P3 上线后的头号监控指标。

**结束**：任何设备判定胜负后，结果以中继收到的多数结果为准，写入 D1，然后关闭房间。

## 7. 防作弊（朋友局，v1 只做基础）

- **中继校验**：指令的座位必须和连接身份一致；指令格式合法；单位 id 必须属于该座位（由模拟层拒绝非法指令）。
- **地图透视风险**：锁步模式下每台设备都持有完整的游戏状态，理论上可以被修改来看穿迷雾。朋友局可以接受；如果以后做公开天梯，需要重新评估。

## 8. 迁移与上线

| 步骤 | 内容 | 验收 |
|---|---|---|
| 3a | Durable Object 中继和协议，本地用 `wrangler dev` 或 Node 模拟中继；无头客户端（Node）2–8 个连接跑完整局 | 8 个无头客户端各跑 10 分钟，校验值全程一致；带宽和延迟统计达标 |
| 3b | 浏览器客户端接入：模拟按轮推进、指令缓冲、表现层即时反馈、等待提示 | 两个浏览器标签页对战，操作延迟 ≤ 200 ms（本机加 100 ms 人工延迟） |
| 3c | 重连、追帧、AI 接管、不同步上报 | 中途断网 30 秒再恢复，状态一致；刷新页面后能追上进度 |
| 3d | 开关上线：大厅里出现“新联机（测试）”选项，旧的轮询联机保留为默认 | **两台真机（如 iPhone 和电脑）实测通过**，再给朋友试用 |
| 3e | 稳定后改为默认；旧联机保留一个版本作为后备，之后删除服务器端的模拟代码 | 一周内没有不同步上报，没有卡死 |

**新增检查**（加入 check-all 和 release-check）：
- 无头 8 人锁步 10 分钟，校验值一致；
- 人为制造 300 ms 抖动和 5% 丢包后仍能完成对局；
- 断线重连；
- 带宽、延迟、中继 CPU 的基准。

## 9. 待决定的事（开工前确认）

1. 指令延迟默认 2 轮（约 200 ms）是否可以接受？同城朋友实际延迟通常 30–80 ms，可以自适应降到 2 轮，再低会增加卡顿等待。
2. 掉线超过 60 秒由 AI 接管，可以吗？
3. 不同步时 v1 采用“多数方为准、少数方退出”，是否接受？v2 再做自动重同步。
4. 一局的录像是否允许玩家下载？这样可以做回放观战功能。

## 10. 成本（沿用 redesign-plan.md）

- 人工 3–4 周；AI 约 5 次会话，约 150 万 token。风险高。
- 最大的不确定性是跨设备一致性，由 `consistency.html` 的真机结果决定。
- 运行成本：每个房间一个 Durable Object，只做转发，开销远低于现在每次请求都要重算整局的做法。具体费用以 Cloudflare 当时的定价为准。
