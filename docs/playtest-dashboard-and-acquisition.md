# 试玩分析 dashboard、细化反馈与获客 — 2026-11-26

## 目标与当前交付

目标是把“招募→下载→游玩→理解反馈→改进→再次验证”变成持续流程。

新增 `tools/playtest-dashboard/index.html`：直接在本机浏览器打开，导入上一版 Android 分享的 JSON 或统一 CSV；查看反馈、已观察会话、可用时长/安装标识覆盖率、停止原因、再玩意愿、阶段时长、规则关键词初筛和玩家原话，导出合并 CSV。无云连接、无真实样本、无默认演示人数，不保存到浏览器存储，不会上传文件。不是已上线或实时 dashboard。

旧报告没有可靠的累计有效游玩时间、安装标识、准确阶段区间；这些卡片显示未采集。现有 APK 仍是源码 33f0633 的离线开发测试包，没有新增云上传或修改游戏。当前文件 dashboard 是独立分析工具，不放进 public/、APK 或公开游戏站点。

## Dashboard 页面与口径

| 面板 | 指标与定义 | 用途 / 限制 |
|---|---|---|
| 总览 | 今天/7天同意统计的活跃安装、会话、对局、有效游玩分钟；每安装与每会话平均/中位数/p90 | 安装标识不是自然人数；标出缺失覆盖率、时间窗、时区；未知时长不能当 0 |
| 实时 | 前台且对局进行中、最近 90 秒获服务端确认的不同安装数；与“停留菜单/暂停”分开 | 在线心跳需约 30 秒一次；页面每 60 秒刷新。离线补传不增加当前在线，不能测未同意统计者 |
| 新手漏斗 | 首次打开→素材就绪→开始对局→首次成功下令/采集/建成/训练→首次交战→完成一局→再次开局 | 用事件成功回执；不能把点按钮当造兵成功。按新手/熟手、设备、版本、渠道分组 |
| 停止分析 | 停止时阶段与局长分布、主动原因、最后一个成功里程碑、错误与失联情况 | 区分完成/主动停止/重开/后台/超时未回报/原生崩溃，失联原因标未知 |
| 时间分布 | 有效对局时间、菜单/教程/建造面板停留、经济/战斗/等待等可复现分类；可选地图粗分区停留 | 时间区间必须去重互斥，分类规则版本化；长停留可能喜欢也可能卡住。地图只存粗分区，不上传逐次点击轨迹 |
| 乐趣 | 最喜欢的部分、具体最好时刻、再玩意愿、再次开局与完整观察窗的 D1/D7 返回 | 意愿与实际行为分开；长游戏时长和完局率不是“有趣”的充分证据 |
| 性能 | 分设备档位/WebView/画质/单位规模的帧间隔 p50/p95、长帧比例、主线程长任务、指令分段延迟、加载/存档耗时 | 首先对照相同场景；后台和菜单不混入战场帧率。单机延迟与未来网络 RTT/锁步等待分开 |
| 错误 | JS 错误类别、原生崩溃/ANR、复现步骤、可选附件 | 当前只存有限 JS 错误行列，不是原生崩溃收集系统。存档/截图需单独同意与容量限制 |
| 反馈与改进 | 问题排名、积极主题、原话、影响版本/设备、证据数、待验证假设、改进事项 | 每个主题按独立反馈/会话计数，不能按同一人的重复措辞放大；点击能追溯原话 |
| 获客 | 渠道访问/下载请求/首开/开局/返回/反馈；每位有效试玩者的招募成本与投入时间 | 下载请求不等于安装，不同渠道不能不分人群直接比较 |

累计 active_seconds：只在游戏前台且模拟未暂停、未结束时累计；另存前台应用时间以区分菜单。RTS 玩家观察战场时可能不点击，不能仅凭键鼠空闲扣掉游玩时间。暂时离开与疑似放弃需等返回窗口并保持未知原因，不能由缺少退出事件自动推断。

对局与会话独立：match_id 跨存档恢复保持；session_id 每次前台游玩段独立；install_id 随机、可重置、只有经同意才用于返回统计。重装、清除标识和多设备会影响安装计数。人工邀请人数仅作招募记录，不强行与标识实名关联。

## 细化反馈表（下一版应用）

不要求每局填长问卷。随时反馈与结算短问卷共用结构，除非需要描述特定故障，其余允许跳过；首次填过的熟练度不反复问。

1. 玩家背景：首次/偶尔/经常玩 RTS；是否首次玩本游戏；不收学校班级、实名或学号。
2. 当前目标：刚才想做什么？例如采集、造兵、海战、登陆、空战、守基地、探索。
3. 主要问题：引导/操作/性能/错误/难度/节奏/内容/视觉音频/其他；附具体步骤、预期与实际。
4. 最喜欢什么：建设成长、指挥战斗、海陆空配合、国家差异、熊猫/特色单位、探索、美术音乐、其他；文字填写一个具体时刻。
5. 最大抱怨：只选最影响本次体验的一项，再允许其他补充，避免一份反馈无限多标签放大计数。
6. 停止原因：还在玩、已完成、临时有事、不会操作、过难/过易、无聊/拖沓、卡顿/错误、其他；不要自动弹窗阻拦系统退出。
7. 再玩意愿：愿意/不确定/不愿意；愿意推荐给朋友及原因可选。
8. 一个最希望的改动：开放文本；区分“玩家提出的解决办法”和“背后真正的问题”。
9. 诊断与附件：当前版本、设置和最小上下文附带说明；性能诊断、截图、完整存档分别选择，不默认附带聊天或个人信息。
10. 是否愿意被追问：可选联系渠道独立保存，与匿名/假名事件表分离。

## 文件格式与已有工具

原始 JSON 保留。CSV 是人可读导出，不替代原始数据；`payload_json` 保留原报告上下文/事件内容。UTF-8 BOM、双引号与换行转义、表格公式注入防护已实现。导出时以 =/+/-/@ 等开头的单元格加单引号，原话的权威副本仍在原始 JSON。CSV 稳定 record_id 用于重复导入去重，不是玩家标识，也不能用于认证。旧报告没有原生 feedback_id 时只能去重完全相同的内容，不能保证识别同一人重复提交的不同报告。

统一 CSV 的 row_type 是 feedback/session/event。当前核心列：record_id、session_id、install_id、build、channel、occurred_at、active_seconds、event、phase、duration_ms、reason、stop_reason、play_again、likes、complaints、suggestions、notes、payload_json。文件 dashboard 的 phase_interval 需上游已经提供去重互斥区间；当前旧 APK 不提供。

```powershell
# 也可直接在 dashboard 一次选择多个 JSON，无需命令行。
node scripts/android/feedback-to-csv.cjs report1.json report2.json > feedback.csv
node scripts/android/check-dashboard.cjs
```

同一 session 的 active_seconds 是累计值，汇总取最大值，不能把每个心跳累加。文件导入只反映收到的样本；手动分享有明显自选择偏差，不能据此推算全体玩家的退出率或留存。

## 实时版最小架构（待实施）

应用内自愿统计 → 限量本机队列 → HTTPS 批量采集接口 → 校验/去重/限流 → 原始事件 + 分钟汇总 → 私有 dashboard。保留文件导入/CSV 导出作为断网与人工分析后备。

上一版 Android APK 已移除 INTERNET 权限；实时版必须明确新增联网权限与独立可关闭的统计同意，不能靠改网页就偷偷获得实时数据。拒绝后照常单机游玩。离线队列设条数/字节/天数上限，后台退避重试；统计失败不等待、不阻断游戏。实时心跳走在线确认，历史批次仅计历史，不“补出在线人数”。首次提交与重试需要稳定事件 ID，重试不能重复加时。

更新频率建议：活跃客户端约 30 秒心跳，在线/总览每分钟汇总；dashboard 每 60 秒刷新或手动刷新；文本归类每小时只分析新增反馈；每日一次版本与渠道摘要。不必每秒调用 AI。显示事件发生时间、服务端接收时间、汇总完成时间和数据新鲜度。跨地区时钟差需校验，不能只信客户端绝对时间。

接收接口不带 APK 内嵌的管理员密钥；公开写接口严格白名单、大小/频率限制、幂等与隔离，不能因为知道来源就信任字段。管理员读取/导出/删除必须认证授权，不把私人反馈 JSON 放入公共静态目录。可评估现有 Worker/D1 后端承载采集，但应将研究数据的访问、保留与删除和游戏房间分开；上线前先明确实际服务地区和中美网络可达性。

沿用前案建议：本地记录上限、云端原始数据 30 天/去标识汇总 90 天（实施前确定）；删除与撤回流程覆盖原始记录和可链接的汇总，基础设施 IP 访问日志同样盘点。对外 AI 文本处理必须说明服务商/地区、去除联系方式、获知情同意后再发送。

## 文本分析输出

当前工具只做关键词初筛，页面已显式标注，不是 LLM 语义分析。下一阶段 AI 输出分开：积极主题、问题主题、功能请求、停止原因、严重度、代表原话、证据数与来源 ID、受影响版本/设备、置信与不确定性、建议假设、验证办法。

数字由数据库计算，模型不能猜人数/时长/比例；不给反馈文本执行命令或修改游戏的权限。原话可纠正模型标签，保留人工复核。否定、讽刺、中英混写和翻译应专门验证。少量样本显示具体 n，不展示虚假的“提升 37%”预测。

例：12/30 份反馈提到不知如何造兵，其中 8 份停在首兵前 → 假设提示不足，先看操作录像/复现，试改训练入口提示 → 验证新手首次训练成功率与用时，并守护画面空间与误触率。这是报告格式示例，不是本游戏实际数据。

## 获客与推荐

“可下载”和“会被推荐”是两件事。独立 APK 下载页没有自动给你带来新玩家的机制；商店上架和被收录也不保证曝光。先主动找到适合 RTS 的成年玩家，拿到体验证据，再放大渠道。

第一批：分别招募约 10 位玩 RTS 的人和 10 位新手，分开记录；美国可从大学游戏/游戏开发社团与独立游戏社区招募，中国可从熟人、大学游戏社团与 RTS 群招募。先取得社群管理者许可，邀请自愿参与，不和课程评价绑定。先问愿不愿意试玩 10–20 分钟，不要求立即完整打完长局。邀请目标是建议，不是必然获客结果。

第二批：准备 15–30 秒真实操作视频、中英文一句话卖点、明确“免费单机试玩/当前缺点”的页面。展示玩家能做什么，例如建设经济→出兵→海战登陆与特色单位，而不是只说“我用 AI 做了一个游戏”。建议分别试 B站/开发日志及海外独立游戏社区/短视频；每次只改变一个视频重点，记录带来的实际开局与返回。

平台顺序：独立下载/网页用于邀请；itch.io 可用于海外试玩页面与开发日志；中国 TapTap 测试能力需按账号与项目资质实际申请；Steam 后续准备公开商店页、准确标签和 Playtest，积累关注/愿望单但不把它当保证推荐的按钮；Google Play 后续优化本地化素材与实际体验。所有渠道当前都未代用户注册、发帖、联系或投放。

不要把学生泛泛地当唯一目标人群。先找愿意玩手机 RTS 的人，才能区分“产品不适合这个人”和“产品做得不好”。熟人反馈与陌生人反馈分开看；手动分享文件者也不代表全部安装者。

每个渠道使用不同非个人代码：campus_us_a、campus_cn_a、bilibili_devlog_01、itch_alpha。网页 UTM 不会自动进入侧载 APK；可以后续使用明确的渠道包标记或首开可跳过“从哪里知道游戏”。若没有安装归因能力，下载→安装转化应标未知。不要用联系人/广告标识补齐归因。

看“访问→下载请求→首次打开→开始一局→有意义试玩→次日返回→愿意反馈”的漏斗。下载量和点赞是辅助；优先比较每小时招募工作带来的有效试玩者、复玩者与可复现问题。初期不急着买量，先修掉让前 20 人无法继续玩的共同问题。

## 本轮验证与边界

`node scripts/android/check-dashboard.cjs` 与 dashboard/analytics JS 语法检查 PASS：旧报告不虚构人数/时长/阶段停留、累计时间不重复相加、重复文件去重、UTF-8/换行/引号、原始 payload、CSV 公式转义与导出再导入稳定 ID、错误输入校验。全部是 Node 逻辑检查，不是浏览器/真机结果。

IAB 预览本轮仍未连上；因此 UI、文件选择/下载、屏幕尺寸、无障碍与文本包含未验收，不宣称已发布或可交给普通玩家使用。没有新部署、自动收集、AI API 调用、真实玩家数据或广告花费。本轮不修改游戏逻辑、不重新生成 APK；原 APK 的源码版本与校验仍见 android-playtest-validation.md。
