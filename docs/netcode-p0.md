# 联机 P0：降低服务器耗时与指令延迟（2026-11-10）

范围：不换架构（仍是 HTTP 短轮询 + D1 乐观锁 + 服务器权威），只做增量改动。分支 `claude/netcode-p0`。

## 结论

- 用户反馈“从一开局就卡”。开局阶段的固定成本有三项，这次都处理了：每次请求恢复存档后重建导航网格（开局 2 人房 p95 142 ms → 43 ms）；每次响应重发全部资源点和迷雾（迷雾关的 2 人开局 174 KB → 37 KB，之后稳定在 10–55 KB）；指令要等下一个轮询周期才发出、单位要等第二个轮询周期才动。
- 自己的单位现在在点击后的下一帧就转向并起步（本地预测，不依赖网络）；服务器确认到达后沿服务器路径平滑并入，不回弹。
- 所有时延数字都是**模型值**（见“度量方法与假设”）。没有做真机、跨设备、线上 Worker / D1 测试。

### 2. 导航网格缓存

- 缓存在 Worker isolate 的模块级 LRU（最多 16 组网格、8 组地形掩码）。键 = 房间号 + 世界签名（`state.world` 的哈希，含地图、种子、人数）+ 静态障碍签名（所有 `hp>0` 建筑的 id / 队伍 / 类型 / 坐标；有城门时再加同盟关系位）。
- 单位移动、碰撞分离、临时阻挡**不**改变键（符合 AGENTS.md）。放置工地、建筑被毁、城墙变化、结盟/宣战（有城门时）会改变键。原有的 `this.grid=null` 失效点全部保留。
- 未命中（isolate 被回收、换了房间、换了种子）时从存档状态正确重建：先用缓存的“纯地形”掩码，再只对建筑周围 264 单位内的格子重新调用 `blocked()`。`check-netcode.cjs` 逐格对比缓存结果与原全图扫描（陆地、海洋、城墙、各队城门）。
- `start()` 与 `advance()`（有步进时）预热陆地和海洋网格。
- **一处有意的规范化**：以前网格由“恢复后第一个请求寻路的单位”构建，建筑留边取决于该单位半径（半径 ≤15 的单位留边 9，火炮/投石机更大）。现在联机里统一按默认行走单位（留边 9）和标准船只构建，网格才成为地形+建筑的纯函数。脚本对局 1200 tick 的状态哈希与改动前完全相同；理论上只有“大型单位恰好第一个寻路”的请求会有差异，且移动时逐步的 `blocked()` 碰撞检查仍按真实半径执行。单机不受影响。
- `Fortification.refreshWalls()` 恢复存档后的第一次计算不再丢弃网格（只有城墙签名真的变化才丢弃）。

### 3. 同步协议 2

- 客户端在请求体里带 `proto:2` 和 `have:{world,tech,nodes,fog}`（它已持有各段的哈希）。服务器对**已按玩家过滤后的视图**计算同样的哈希，相同则不再发送该段。
- 迷雾：`visible`/`explored` 由两个约 20 KB 的 JSON 数字数组改为 base64 位图（各约 1.7 KB）。
- 资源点：拆成静态字段（`nodeStatic`，可见集合不变就不重发）和动态字段（`nodeDynamic`：储量、记忆标记、狩猎进度）。
- 客户端若收到省略了自己并不持有的段，会丢弃该视图并在下次请求不带哈希重取（`check-netcode.cjs` 覆盖）。
- 兼容：不带 `proto` 的请求得到与以前相同结构的响应；`/api/health` 保持 `protocol:1`，新增 `sync:2`，`version` 13 → 14；房间对象新增 `proto:2`，客户端据此决定是否使用 `orders`。存档格式（D1 中的房间行）没有变化。
- 安全过滤未放宽：未发现的军队、记忆建筑、对手经济/科技/队列、他人迷雾仍在 `networkSnapshot()` 的过滤之后才编码；伪造别人的哈希只会拿到自己的完整段。

### 4. 合并指令

- 客户端在 `beginOrders()`/`endOrders()` 之间收集逐单位的 `order()`，发一条 `orders`：移动类带每个单位自己的编队落点（`points`），攻击/采集/建造/维修类带 `each:true`。
- 服务器对每个单位走与原 `order` 完全相同的 `orderUnits()` 校验（所有权、目标、视野、地图边界）；某个单位被拒不影响其余单位（与原来逐条发送一致），全部被拒才返回错误。
- 限流不放宽：一条合并指令按其中的单位数计入每席位 2 秒 320 的突发上限。

### 5. 客户端

- 下令后立即发起请求（同一次点击里的多条指令共用一个请求；已有请求在途则在其返回后 30 ms 发出）。
- 轮询节奏：下令后 1.5 秒内 200 ms；正常对局 350 ms（不变）；场上无移动/战斗/队列时 550 ms；标签页隐藏时 1000 ms。
- 本地预测：移动/推进指令使所选单位下一帧转向并沿直线起步，直线在第一个不可通行格子前截断。预测只改“画在哪里”，不改指令、资源、队列；服务器 1.5 秒内未确认则平滑回到权威位置。
- 外推与校正：两次同步之间，己方单位沿服务器路径按自身速度前进，他人单位按最近观测速度外推（最多 0.9 秒）；新权威位置到达后以 0.5×–1.75× 速度沿路径并入，而不是向后拉回；终点前 38 单位（服务器的到达半径）不外推。

## 未验证

- 没有在 iPhone / iPad / 任何真实浏览器里运行过新的客户端代码；`network-ui.js` 的轮询节奏只做了语法检查和代码审阅，`network-client.js` 的预测逻辑在 Node 的 `vm` 里用真实模拟验证。
- 没有部署到 Cloudflare：isolate 复用率、D1 往返时间、真实冲突率、Workers 上的 CPU 速度都未知。isolate 复用率低时网格缓存的命中率会下降（每次未命中约 60–170 ms，仍低于改前每次请求的 150–900 ms）。
- 没有跨设备、弱网、丢包、后台恢复测试。
- 预测只覆盖移动/推进指令；攻击、采集、建造指令只立即转向，位移仍等服务器。
- 被服务器拒绝的移动指令会有一次最长 1.5 秒的预测后平滑回退。
- 攻击/采集类指令在战斗中被单位碰撞挡住时，外推可能领先权威位置最多约 0.5 秒路程，再被纠正。

## 预期与剩余瓶颈

- 朋友间 2–4 人、200 单位以内：服务器单次请求 20–70 ms，轮询周期能保持在 350 ms 目标值；自己的单位点击即动；别人的单位显示延迟约 0.5–0.9 秒（一个轮询周期 + 往返 + 平滑）。
- 只靠这些改动的下限：权威位移可见约 0.45–0.8 秒（RTT 40–100 ms 假设），指令确认约 0.16–0.4 秒。这是 HTTP 轮询 + 每请求整行读改写的结构性下限。
- 500 单位以上的大会战仍然慢（单次请求 240–370 ms，模型时延 2–3 秒）：成本来自每次请求解压/恢复/重算迷雾/重建索敌名册和模拟本身，而不是网格。
- 仍需锁步 + Durable Object（或常驻内存的权威 DO）才能解决的：他人单位延迟降到 200 ms 级；去掉每请求的存档解压/压缩与 D1 写（现在每次轮询一次整行写，免费额度约 1–2 小时/天）；去掉乐观锁冲突重算；满编会战。
- Cloudflare Workers 免费计划每请求 10 ms CPU 上限：现在开局请求 p50 约 18 ms，仍超限，需要付费计划。此数字来自 Cloudflare 公开文档，未在控制台核实。
